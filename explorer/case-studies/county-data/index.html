Case study 02 · Data integration

Making county data usable.

Building batch ETL importers to transform inconsistent county exports into a unified database used by applications and customers.

SourcesCounty batch exports
ApproachCounty-specific importers + shared logic
OperationManual runs and error resolution
Context

Different counties, different data

Each county supplied batch exports, rather than direct database access. File formats and schemas varied by county. The application needed standardized information in a common database.

Design

Reuse without forcing uniformity

I worked with county-specific importers to accommodate source quirks, sharing common processing logic where it made sense. A fully generic importer would not have reflected the real variation in county exports.

Architecture

Batch transformation pipeline

County file exports→County-specific importers→Unified database→Customer applications

This is a conceptual data flow, not a claim about specific infrastructure or deployment topology.

Operation

Manual processing and recovery

Imports were triggered manually. New batches replaced the county's previous dataset. If processing encountered an error, the import stopped and reported it; we resolved the issue manually before continuing.

Tradeoffs

Historical data was considered, not built

I saw potential value in retaining historical datasets for change tracking, traceability, and future features. We did not implement retention because an immediate business justification was lacking. That distinction is important: it was a considered opportunity, not a delivered capability.
